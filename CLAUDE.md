# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

    cargo test                          # unit tests; run from the repo root, they load assets/ by relative path
    cargo test <name>                   # single test, e.g. cargo test falling_box
    cargo test --release -- --ignored --nocapture   # benchmarks in src/bench.rs
    cargo fmt && cargo clippy --all-targets -- -D warnings
    cargo test --no-default-features    # lean build: software renderer, no audio (29 crates, ~10 s clean vs 122 crates, ~35 s)

`ENGINE_MUTE=1` silences audio, `ENGINE_STATS=1` logs frame timings and `ENGINE_RENDERER=soft|gpu|auto` picks the renderer (see the GPU backend note under Architecture). The window needs an X display (WSLg works); `minifb` is built with the `x11` feature only, because its Wayland backend spams EGL/Zink errors under WSL.

Commits are checked by pre-commit (`pre-commit install`): Conventional Commits (`feat|fix|refactor|perf|test|docs|chore|ci|build`, optional scope), plus `cargo fmt --check` and clippy with `-D warnings`. There is no CI; run `cargo test` yourself.

## Project conventions

- Comments are allowed but rare: add one only where the code cannot show *why* (a non-obvious constraint, workaround or invariant). Keep it to one short, plain line. Never restate what the code does, and skip doc comments on self-explanatory items. The owner dislikes comment-heavy code.
- `rustfmt.toml` uses `max_width = 120` and `use_small_heuristics = "Max"`, so short bodies stay on one line. Run `cargo fmt` rather than formatting by hand.
- Keep changes minimal; measure before optimizing (see `src/bench.rs`).
- Reuse before writing: `Rect::center/contains/edges/penetration/overlaps`, `Sprite::bounds`, `DrawCmd::new`, `Paint::region` (sprite and region paints alike), `assets::read_text(_if_exists)` for files and the `sub/dot/apply/shove` helpers in `physics.rs` already exist; add to them rather than repeating the arithmetic.

## Architecture

`engine` is a library crate. Source is grouped by area (`app/`, `render/`, `ecs/`, `assets/`) and `src/lib.rs` re-exports the whole public API at the crate root, so games and internal code use flat `engine::X` / `crate::X` paths and never reach into the folders. Games use only that API, never `minifb` directly.

**Loop and scenes (`app/`).** `run(cfg, first)` owns the window, a fixed-timestep accumulator (`Config::tick_hz`, default 60) and a scene stack. A game implements `Scene { update(&mut self, &mut Ctx) -> Trans, draw(&self, &mut Gfx) }`. Only the top scene updates; every scene draws, bottom first, so overlays like pause draw over what is beneath. `Trans` (`None/Push/Pop/Replace/Quit`) drives the stack, and an empty stack ends the program. `on_enter` runs when a scene joins the stack (initial, `Push`, `Replace`) and `on_exit` when it leaves (`Pop`, `Replace`, `Quit`, window close); a `Push`ed overlay does not touch the scene beneath. Game scenes call `ctx.cam().reset()` in `on_enter`, and anything that outlives a scene (music) is stopped in `on_exit`. `Ctx` fields are crate-private and reached through accessors (`input()`, `assets()`, `audio()`, `cam()`, `rng()`, `dt()`, `size()`), so games cannot replace a subsystem or write `dt`. Each accessor borrows the whole `Ctx`: read `let dt = ctx.dt();` into a local before a call like `ctx.cam().follow(.., dt)`, never nest them. `first` is a closure taking `&mut Ctx` because scenes load assets in their constructors. The engine does not handle Esc; scenes do. `Trans::Fade(Box<Trans>, secs)` wraps another change in a fade to black: the top scene stops updating while the screen darkens over `secs / 2`, the inner change is applied at full black, and the picture comes back over the other half (`app/fade.rs`; the black is one `fill_alpha` over the whole picture after the scenes and before the debug line, so it needs no backend support, and the fade state lives in `Ctx`). A new `Fade` while one is already darkening cannot happen (nothing updates); one returned while fading back starts over from a clear picture (the black jumps to nothing first). Only the phase logic has a unit test; the loop wiring in `run` was not run in a window. `run` draws and presents only on frames that ran at least one tick (and the very first), sleeping until the next tick otherwise, because nothing changes between ticks: drawing on every loop pass is about 190 identical frames per second where 60 are needed, which costs CPU (about 73% against 22% in the software path, 45% against 19% on the GPU path) and three times the presents over a remote display. F3 (debug overlay) is handled in `run` by tracking its previous state itself, because `Input::pressed` only refreshes once per fixed step and would misfire on frames that run no step.

**Rendering (`render/`).** `Gfx` does not draw: it records `DrawCmd`s (`fill`, `fill_alpha`, `outline`, `blit`, `blit_region`, `clear`, `draw`, and `text`, which records one `Glyph` command per visible character of an 8x8 ASCII bitmap font, scaled by an integer) into a per-frame list, in screen space. `run` hands that list to a backend and resets it. `Soft` (`render/soft.rs`) rasterizes into a `Vec<u32>` (0xAARRGGBB sprites, 0xRRGGBB framebuffer; plain `fill` ignores alpha, `Alpha` blends 0-255); it starts every frame from black, so a frame is exactly its command list. The camera is applied when world-space commands enter `Gfx::draw` (it subtracts `gfx.cam`, skips debug-only commands unless `gfx.debug`), not by `fill`/`blit`/`text`, so HUD text drawn directly with `gfx.text` stays in screen space. `Tilemap::draw_list(gfx.view())` produces the visible tiles as one or two world-space `Tiles` commands (behind and in front of entities; each is one sheet reference plus a list of grid offsets and tile ids relative to the command's rect), or none when nothing is visible; backends loop over that list, so the sprite sheet is cloned and uploaded once per frame instead of once per tile. `render/` knows nothing about the ECS; `DrawCmd` is the whole contract between them, so any backend only has to consume that list.

**Cargo features.** `gpu` (wgpu, pollster, bytemuck) and `audio` (rodio) are both on by default and each pulls in dozens of crates; without them the engine still builds and runs with the `Soft` renderer and a silent `Audio` whose methods do nothing (the stub does not even read the sound file). `RenderMode::Gpu` / `ENGINE_RENDERER=gpu` in a build without `gpu` prints one stderr line and uses `Soft`. Code touching those crates must stay behind `#[cfg(feature = ...)]`; pre-commit runs clippy for both the default and the `--no-default-features` build, so a leak fails the commit. Prefer in-house code or tiny crates over new dependencies: build time is a stated concern.

**GPU backend (`render/gpu.rs`).** `Gpu` (wgpu 30) consumes the same `DrawCmd` list: every command becomes quads in one dynamic vertex buffer (pixel coordinates, converted to NDC in the shader), solid fills sample a 1x1 white texture, glyphs sample a one-row atlas of the 128 ASCII glyphs built once at start-up and tinted by the vertex colour, and each `Arc<Sprite>` is uploaded once (keyed by pointer, kept alive) with consecutive same-texture quads merged into one draw call. Fills and sprite origins are truncated the way `Soft` does, so the two backends produce the same pixels. The surface is created from the minifb window's raw handles (`create_surface_unsafe`; `run` drops the backend before the window) and uses a non-sRGB format with nearest sampling. `Config::renderer` is `RenderMode::{Auto, Gpu, Software}` (default `Auto`) and `ENGINE_RENDERER=auto|gpu|soft` overrides it: `Auto` takes the GPU only when a non-CPU adapter can present to the window and otherwise falls back to `Soft` with one stderr line; `Gpu` also accepts CPU adapters (llvmpipe, much slower than `Soft`). Under WSL Mesa only exposes the real GPU through its D3D12 driver, so `run` sets `GALLIUM_DRIVER=d3d12` itself when `/dev/dxg` exists and the variable is unset; that GL adapter can occasionally fail to initialise, which also lands on the `Soft` fallback. In the WSLg setup the display transport costs about 4 ms per frame on either backend, so the GPU only wins as scenes get heavy (thousands of sprites, full-screen blends). `ENGINE_STATS=1` prints fps, tps, update/draw ms and present ms every second. The test `gpu_output_matches_the_software_rasterizer` renders one scene on both backends off-screen and compares every pixel (per-channel tolerance 2 for blending rounding), skipping when no adapter exists; set `ENGINE_DUMP=<dir>` to also write `soft.png` and `gpu.png`. The texture cache keys sprites by `Arc` pointer and holds a clone to keep the key unique; at the start of each frame it drops entries nobody else references (`strong_count == 1`), so a sprite a game creates and drops frees its texture (otherwise every dropped sprite would leave one behind). Sprites held by `Assets` are never evicted.

**Rotation and scale.** Every `DrawCmd` carries a `Transform { angle, sx, sy }` (identity by default); as an ECS component the same type on an entity is copied into its commands by `draw_list`. The angle is in radians, clockwise on screen (y points down); scale multiplies the drawn quad's size, a negative scale mirrors, zero draws nothing. Both always pivot on the centre of the drawn quad: for `Color`/`Alpha` that is `rect`, for `Sprite` and `Region` it is the natural size placed at `rect.x, rect.y`. Text (`Glyph`), `Tiles`, `Outline` and `Clear` ignore it on purpose. An identity transform takes the original axis-aligned paths untouched. `Gpu` transforms the four corners (`warped`); `Soft::warp` walks the destination bounding box and maps each pixel centre back into the source (nearest texel, no anti-aliasing), so a pixel is covered when its centre is inside the quad on both backends. A test renders a mixed scene on both and compares: no pixel differs on llvmpipe or on the real GPU. `Soft` pays per pixel: 2000 rotated 16x16 sprites cost about 3.7 ms against 0.6 ms unrotated (`warp` steps `u` and `v` along each row instead of redoing the matrix per pixel; it was 6.1 ms), so heavy use of rotation belongs on the GPU backend. Debug outlines stay axis-aligned.

**Alpha fills and CPU dispatch.** `Soft::fill_alpha` blends a row at a time with `blend` (in `render/soft.rs`), a SWAR formula: R and B are masked into one `u32` with an empty byte between them so one multiply handles both, the divide by 255 becomes `>> 8`, and alpha is mapped to 0..=256 (`a + (a >> 7)`) so 0 and 255 are exact; results stay within 1 of exact division. The same loop is compiled twice, plain and with `#[target_feature(enable = "avx2")]`, and `blend_row` picks one with `is_x86_feature_detected!` at run time, so the default build gets AVX2 code on CPUs that have it without `-C target-cpu=native`. Both paths run the same arithmetic and must stay bit-identical (a test checks it). Full-screen alpha costs about 0.125 ms on the plain path and about 0.07 ms with AVX2 (a per-channel division cost 0.234 ms). Measure changes like this on the real path, not in an isolated loop: the type of the alpha argument alone moved an isolated benchmark by 1.6x.

**Scaling.** `Config::scale` (integer, also `ENGINE_SCALE=n`) makes the window `scale x` the internal resolution (`w`, `h`); the game, camera and `DrawCmd`s stay in internal pixels. `Gpu` just configures the surface at the larger size, since vertices are already mapped onto the whole viewport and sampling is nearest, so enlargement is free and pixel-exact. `Soft` renders at internal size and `upscale` (in `render/soft.rs`) expands each source row horizontally with `chunks_exact_mut(scale).fill` and then duplicates it with `copy_within`, about 0.4 ms at x2 and 0.8 ms at x3. In the WSLg setup the cost of presenting grows with the window's pixel count (about 4 / 9-14 / 18-21 ms per frame at x1 / x2 / x3), so large scales are display-bound, not engine-bound. `Config::resizable` (default true) lets the player drag the window to any size: the picture keeps its shape, is centred (`letterbox` in `render/gfx.rs`) and the rest is black. `Soft` leaves it to minifb (`ScaleMode::AspectRatioStretch`, nearest, so a non-integer factor makes uneven pixels); `Gpu::resize` reconfigures the surface and `fit` sets a viewport on the render pass (a test renders off-screen into a window of another shape and checks the bars stay black), and `run` redraws on the frame the size changes. minifb 0.29 has no fullscreen call and no way to set the size from code, so fullscreen is the window manager's maximize, not an engine feature.

**Camera (`render/camera.rs`).** State lives in `ctx.cam` and is advanced in the fixed update, not in `draw`: scenes call `ctx.cam().follow(target, world_size, dt)` (eases toward the target with a frame-rate-independent factor, clamped to the world; the first call snaps) and `ctx.cam().shake(amplitude_px, secs)` (random jitter that decays linearly). `cut()` makes the next `follow` snap, for teleports and respawns. `run` copies the final whole-pixel offset into `gfx.cam` before drawing, so tiles and entities do not jitter against each other. The camera is one per app and persists across scenes, so scenes reset it with `ctx.cam().reset()` in `on_enter` when they need a clean view.

**ECS (`ecs/`).** `World` and `Entity` come from `hecs`. The engine ships only components every game needs (`Body(Rect)`, `Vel`, `Look`, `Anim`, `Collider`, `Layer`) and these systems: `movement`, `animate`, `particles`, `draw_list` (turns `Body` + `Look`/`Anim` entities into a sorted `Vec<DrawCmd>`; games draw with `gfx.draw(draw_list(&world))`); games define their own components and logic inside `Scene::update`. hecs requires components to be `Send + Sync`, which is why `Assets` hands out `Arc<Sprite>`, not `Rc`. In hecs 0.11, `query`/`query_mut` iterate plain items (no `(Entity, ...)` wrapper); ask for `Entity` explicitly in the query tuple when you need it.

**Collisions (`ecs/`, `render/tilemap.rs`).** Two separate mechanisms. Entity vs entity: `collisions(&world)` returns `Contact`s for overlapping `Body` + `Collider` pairs using sort-and-sweep on x; contacts carry penetration depth per axis, and `Contact::x_axis()` says which axis to bounce on. It only reports overlaps; resolving them is either up to the game or done by `Physics` below. Entity vs terrain: `Tilemap::slide` moves axis by axis and snaps to tile edges, assuming per-step movement smaller than a tile. Screen borders are handled by game code, not entities. `Filter { group, mask }` (optional; none means every group and mask) limits who meets whom in both `collisions` and `Physics`: two entities meet only when each one's mask holds a bit of the other's group. Tiles are group `Filter::TERRAIN` (bit 31), so clearing that bit in a body's mask lets it pass through the map. A `Collider` without a `RigidBody` is a trigger: `collisions` reports its overlaps and physics ignores it. `raycast(&world, from, dir, max, mask)` returns the nearest `Collider` whose group is in `mask` with its distance factor (a linear scan that shrinks its range as hits come in, about 45 us per ray over 3000 colliders; it follows `Transform::angle` like physics and ignores scale). For many rays against one world build `RayIndex::new(&world)` once and call `index.cast(..)` (same arguments and answer): it puts the colliders' turned bounds on a uniform grid (cell about the mean box size, at most 65536 cells, a box is in every cell it touches) and walks a ray through the cells it crosses with a DDA, stopping at the first cell that ends beyond the best hit; building 3000 colliders costs 0.17 ms and a ray 0.1-0.2 us in the dense bench scene (rays that cross the whole grid cost more, up to about one test per cell crossed). It is a snapshot, so rebuild it after bodies move, and a test checks it against the scan over random boxes, turns, groups and rays and `query_rect(&world, &rect)` lists the colliders overlapping an area; neither looks at tiles. A body a filter ignores still wakes a sleeping physics body it moves through, because waking looks only at bounds.

**Physics (`ecs/physics.rs`).** In-house rigid bodies for boxes and circles with rotation, no dependency. Give an entity `Body` + `Vel` + `RigidBody::dynamic(mass)` (`.with_bounce(e)`, `.with_friction(mu)`, `.with_spin(rad/s)`; defaults 0, 0.4, 0) and call `physics.step(&mut world, Some(&tilemap), dt)` once per fixed update; `.circle()` makes the body a circle inscribed in its (square) `Body` rect, radius `min(w, h) / 2`; `RigidBody::fixed()` is a wall (infinite mass, stored as `inv_mass = 0`, so one formula covers both cases) and needs only `Body`. **Rotation is opt-in by adding a `Transform` component** (the same one the renderer draws with, so what you see is what collides): physics reads `angle` from it, turns the body about the centre of its `Body` rect (which stays the *unturned* box, so it is no longer the body's bounds), writes the new angle back, and keeps the angular velocity in the public `RigidBody::spin`. A dynamic body without `Transform` never turns (zero inverse inertia); a `fixed` body with one is a tilted wall or ramp. `sx`/`sy` are ignored by physics. Inertia is a solid box `m (w^2 + h^2) / 12` or disc `m r^2 / 2`. A body without `Vel` never moves. `Collider` is a separate marker for `collisions()` and is not needed here; entities without `RigidBody` (a paddle moved by game code) are ignored by physics. One step is: gravity into velocity, position and angle by the new velocities (semi-implicit Euler), solid tiles near each dynamic body (by its rotated bounds) joined as fixed boxes (`Tilemap::solid_in`; the map edges left and right count as solid), overlapping pairs from `overlapping_pairs` (sweep and prune over each node's `bounds()`), then `touch(a, b)` makes a contact: a normal from a to b plus one or two points with their depths. Cases: two untilted boxes (`axis_aligned`: the two ends of the overlap segment), two boxes of which one is tilted (`tilted_boxes`: separating axis test over the four face normals, reference face of the shallower axis, incident edge clipped to its side planes, like Box2D-lite), circle-circle by centre distance, circle-box in the box's own frame by the closest point. `iterations` (default 10) sequential-impulse passes then run over the contact points with *accumulated* impulses (clamped at zero, so a pass may take back an over-push) and the angular terms `(r x n)^2 / I` in the effective mass: normal impulse towards the bounce speed (restitution times the closing speed measured once before the passes, zero below 30 px/s so resting contact does not bounce), then Coulomb friction clamped to mu times that point's accumulated normal impulse (mu = sqrt(mu_a mu_b)), which is what makes a ball roll rather than slide. Then 6 positional corrections (up to 50 while any contact joins two movable bodies more than 4 times apart in mass and is still deeper than 0.07 px: a light body between a floor and a 100x heavier one sank 9 px with 4 passes and 0.7 with the extra ones; the same extra passes on every pile made a 300-body pile jitter at 13 px/s, and 1000x is still about 10 px) move bodies (not angles) by 50 percent of the depth beyond a 0.02 px slop, split by inverse mass; the depth shrinks by how far the two centres have already moved together along the normal (`Node::at`). Untilted boxes take their contact direction from where the two boxes were *before* the step (`before`), not from the current overlap: judging by the shallower overlap or by the centres makes a fast or thin body, once it is deeper than half the thing it hits, get pushed through it (two regression tests cover this; each fails without its fix); a circle whose centre ended up inside a box leaves by the side it was on before the step for the same reason. Tilted boxes and circles have no such history, so substepping is what keeps them in. Fast bodies: `step` cuts the step into `substeps` shorter ones (at most `MAX_SUBSTEPS`, 16) until no body moves more than an eighth of its smaller side per substep (`TRAVEL`; it was a half, see the shaking notes below), which stops tilted boxes and circles tunnelling too; the whole world substeps, so one bullet costs everyone, and above 16 substeps (about 960 px/s for an 8 px body, 4 times lower than before the eighth, though it is never subdivided less than before) it can still pass a thin wall. Known limits: no true continuous collision detection; a stack of N boxes needs roughly more iterations as N grows (residual speed in a 4-box stack: about 6 px/s at 8 iterations, 2.7 at 12, 0.35 at 24); piles press boxes into each other by up to about 1 px. Tile contacts are filtered so floors have no ghost bumps: for untilted boxes a face hidden by a neighbouring solid tile is dropped whole (the `behind` check in `find_hits`), for everything else each contact *point* on a tile's boundary is dropped when a solid neighbour lies on the body's side of it (`is_hidden`); without that, a body walking on a floor catches on every seam, because its resting 0.02 px overlap makes the seam look like a wall (a walking body exposed it), and a ball touching a tile corner would bump over the seam instead of rolling. If that leaves a tilted box with nothing (its face met a seam corner), the contact is recomputed with only the tile's axes so the box's vertex meets the tile's face, which is the real contact; without that it fell through floors. Tiles always go second in a pair so the filters see them. Tests: rolling down a 30 degree ramp accelerates at `g sin(a) / 1.5` with spin `v / r`, an off-centre hit conserves linear and angular momentum, tilted boxes settle flat on plain and tiled floors. Contacts are warm-started: `Physics` remembers each body pair's final impulses per point (`cache`, pairs named by entity bits, tiles by position) and `warm_start` replays them next step when the normal is within about 18 degrees and the point is within 4 px, which is why `step` takes `&mut self` and `Physics` is built with `..Default::default()` outside the crate. Every `prepare` must run before any replay, because replaying changes the closing speeds that decide bounce (doing it per contact made piles explode). A 1000-body pile averaged 40 px/s of residual jitter before and 0.3 after. Measured (release, `src/bench.rs`, half circles and half boxes of 8 px settled in a 640x360 arena): a pile that has fallen asleep costs 0.02 ms per step at 100 bodies, 0.11 ms at 300 and 0.33 ms at 1000; awake it was 0.12, 0.37 and 1.95 ms, so the broadphase needs no grid yet. Sleeping: a body below 5 px/s and 0.1 rad/s for half a second (`doze`, `Rest`) sleeps: `freeze` gives it zero inverse mass for the step so it is a wall, zeroes its `Vel`, and costs no solving. It wakes when a body faster than 20 px/s (`WAKE_SPEED`; above the 5 px/s a body may sleep at, so one creeping at the edge of sleeping does not keep waking the bodies it touches, which kept whole clusters from ever resting) has bounds (grown by one step of travel) overlapping it, or when the game changed its `Body`, `Vel` or spin (compared with the rect stored at sleep time); `physics.asleep(e)` and `physics.wake(e)` expose it, and `wake` wakes one by hand. Everything all sleepers rest on is watched as a whole: a body that vanished, a changed `gravity`, or a changed tile map (`Tilemap::stamp`, a number that is new for every map and after every `Tilemap::set`) wakes every sleeper (only the sleeping stops, the time a body has been still keeps counting, so one whose support is still there is asleep again within the step), so digging a tile or despawning a floor lets the bodies above fall. Jointed bodies never sleep. Shaking in dense piles (`src/bench.rs`, `shake`: 100 to 300 boxes of 14 to 34 px with random turn, spin, bounce 0 to 0.7 and mass `size^2 / 100`, dropped in rows into the 640x360 arena, averaged over 8 seeds, the first second ignored): what shook was contacts that were already deep when they first appeared, not normals flipping (99 percent of the contacts over 6 px deep had no contact the substep before, and only a handful of known pairs ever changed their normal by more than 37 degrees). A body was allowed half its smaller side per substep, but two bodies closing on each other cover twice that and a hit can speed one up mid-step, so a 14 px box met its neighbour 6 to 10 px deep and the positional correction then threw bodies 12 to 20 px, which is also how bodies ended up under the floor. Cutting the allowance to an eighth (`TRAVEL`) took the 100-body pile from 5740 steps in which an awake body's centre moved over 6 px to 564, the 200-body pile from 39700 to 3800, the 300-body pile from 73000 to 12500, and the bodies under the floor from 4, 41 and 104 to 0, 0 and 11, without raising the average step cost (0.10, 0.25 and 0.8 to 1.1 ms; worst step about 10 ms). Two earlier changes belong to the same fix: sleepers are woken only above `WAKE_SPEED` (20 px/s, with sleeping at 5), because a body creeping at the edge of sleeping used to keep waking the ones it touched so that whole clusters never rested (one 100-body pile never slept: 39000 jumps over 1.5 px), and positional correction is 50 percent over 6 passes instead of 80 over 4. With the finer substeps the old 80 percent is much worse (11000 steps over 6 px at 100 bodies), 30 percent shakes least but fails `a_stack_of_boxes_settles_without_sinking_or_jittering` and the squashed-light-box test, and more passes on lopsided piles (up to 160), capping the shift per pass at 2 px and more `iterations` (10 to 40) each did worse or nothing. An eighth is not the end of the scale: a sixteenth gives 93 and 2100 big jumps at 100 and 200 bodies but a worst step of 16 ms at 300. Left: 300 such boxes fill about 87 percent of the arena, which cannot settle without shoving, and piles settle slower than before in some cases (200 bodies: 4.1 s to 8.8 s until everything sleeps). Joints: `physics.rod(a, b, length)` keeps two body centres a fixed distance apart and `physics.rope(a, b, length)` only stops them getting farther; both cancel the velocity along the joint inside the solver loop and pull positions back in the correction passes, ignore torque (the ends are the centres), are looked up by entity every step so a despawned end silently disables the joint, and stay until `clear_joints()`.


**Layers and particles.** `draw_list` sorts drawables by `Layer(i32)` (default 0, stable within a layer, so spawn order breaks ties). Particles are ordinary entities (`Body`, `Look::Color`, `Layer(10)`, `Particle`) created by `burst(world, ctx.rng(), at, &Burst{..})` and advanced by `particles(world, dt)`, which fades them out (`Look::Alpha`) over their life, despawns them, and moves them itself: they carry their own velocity instead of `Vel`, so they are not double-moved by `movement` and games whose player uses `Vel` without `movement` still work. `ctx.rng()` is the shared seeded `Rng`.

**Time helpers (`app/time.rs`).** `Timer::once(secs)` / `Timer::looping(secs)` accumulate the fixed `dt` you pass to `tick(dt)`; `tick` returns true on the step a once-timer finishes (or a looping one wraps), `fraction()` is progress in 0..=1 (so fades are `1.0 - fraction()`), and a zero-length once-timer is done from the start. `Ease` maps progress through a curve (`Linear`, `InQuad`, `OutQuad`, `InOutQuad`, `OutCubic`, `OutBack`, which overshoots 1 on purpose); `Tween::new(from, to, secs, ease)` combines the two (`tick(dt)` returns the value, it lands exactly on `to`). Camera shake and particle lifetime use `Timer`; `Anim` keeps its own wrapping clock because `play` changes its duration mid-run.

**Panels and atlases.** `gfx.blit_nine(&sheet, src, margin, &dest)` draws a framed region of a sheet as a panel of any size: the `margin` wide corners keep their size and the edges and middle are *repeated*, not stretched (`Paint::Region` only draws at natural size and the backends have no scaling path, so tiling keeps pixel art crisp and needs no backend change), the last repeat cut short; it records one `Region` command per piece (a 200x100 panel on an 8 px middle is a few hundred, which the GPU merges), a middle of 1 px would be a command per pixel row, and it panics if `dest` cannot hold both margins. `Atlas::parse(sheet, text)` / `Atlas::load(sheet, path)` name regions of a sheet from a text file with one `name x y w h` per line (`#` comments, blank lines skipped; a repeated name, an empty region or one outside the sheet is an `Err` naming the line); `atlas.get(name)` is the `Rect` (panics on an unknown name, like a missing asset) and `atlas.draw(gfx, name, x, y)` blits it. It is not hot-reloaded and `Assets` does not cache it.

**Animation.** `Anim` treats a sprite sheet as a grid of equal frames: a row is a clip, `play(row, frames, fps)` selects it (and restarts only when the row changes), `flip` mirrors horizontally. Call `animate` each step; within one layer, `Anim` entities are listed after `Look` ones.

**Audio (`assets/audio.rs`).** `ctx.audio().play(path)` fires a one-shot, `music(path)` loops one track. `set_volume(v)` is the master volume and `set_music_volume(v)` the music's own, both clamped to 0..=1 (default 1; `volume()` and `music_volume()` read them): `set_sfx_volume(v)` is a third bus for one-shots, so they start at master times sfx and the playing music follows master times music at once, but a one-shot already playing keeps the volume it started with. The numbers live in one `Mix` struct shared by the real and silent builds (same `Audio` type, the device fields exist only with the `audio` feature), so a volume slider works in both. `music_fade_in(path, secs)` starts a track from silence and `music_fade_out(secs)` takes the current one down (from wherever a fade had got) and stops it; the fade is a separate gain multiplied into the music volume, so it never overwrites the player's `music_volume` setting, and `run` advances it once per fixed step (`Audio::tick`). `play` keeps its `Player`s and allows at most `set_max_sounds(n)` at once (default 32): a new one cuts off the oldest. Only the numbers are tested (no sound files ship any more, and nothing here was listened to). File bytes are cached, decoding happens per play. Set `ENGINE_MUTE=1` to skip opening the device entirely (use it for automated or repeated runs). If no output device opens, audio disables itself with one stderr line and every call becomes a no-op, so games never fail on audio. Under WSL, ALSA needs the PulseAudio plugin (`libasound2-plugins`) to find WSLg's sound server.

**Levels.** `Tilemap::load(path, ...)` reads a plain-text grid, one row per line, all rows the same width: `#` ground and `+` brick are solid tiles, `.` or space is empty, and any other character is a marker the game queries with `map.marks(b'P')` (pixel position of the tile's top-left). `Tilemap::try_load_with(path, size, sheet, &legend)` (and `try_from_ascii_with`) takes your own `Tile { ch, id, solid, front, auto }` entries instead of `Tile::DEFAULT`: `id` is the sheet column plus one (the sheet is a row of square tiles; `assets/images/tiles.png` has ground, brick, a dark wall and leaves), `auto: true` makes `id` the first of 16 consecutive sheet tiles picked at draw time by which neighbours of the same id are joined (up 1, right 2, down 4, left 8, the map edge counts as joined; `draw_list` looks at the neighbours, the stored tiles, collision and `set` keep the base id; the other 15 ids belong to it, and a sheet that is too short or a legend entry using one of them is an `Err`), `solid: false` tiles never block bodies, and `front: true` tiles are drawn over entities (`draw_list` returns up to two commands, on layer `i32::MIN` and `i32::MAX - 1`). The flags belong to the id, a character the legend does not name is a marker, and a legend entry for `.`, space or id 0, or with an id past the sheet's tile count, is an error. `Gfx::draw` sorts what it is given by layer (stable), which is what lets one `cmds` mix map and entity commands. `tile(tx, ty)` and `set(tx, ty, id)` read and replace a cell (an id no entry names is solid and behind; an id past the sheet's tile count panics in `set`, because drawing it would read outside the sheet).

**Hot reload (`assets/watch.rs`).** `Config::hot_reload` (default: on in debug builds, off in release) makes `run` poll the modified time of every watched file twice a second; no file-watcher crate. `Assets::sprite` and `ctx.load_bindings` watch their files automatically. A changed image is decoded and swapped *inside* the existing `Sprite` (it is an `RwLock<Image>` plus a version counter), so every `Arc<Sprite>` already held by entities, animations and tilemaps shows the new pixels; the GPU backend compares the version and re-uploads that texture. A changed bindings file is re-applied. Decode or parse errors keep the last good data and print one line, because a half-saved file is normal during editing. Level files are the game's business: `ctx.watch(path)` once, then `if ctx.changed(path) { ... }` (true once per change) and reload with `Tilemap::try_load` (the `try_` variants return `Err` instead of panicking). `ctx.changed` only fires for paths that are being watched.

**Assets and input.** `ctx.assets()` caches sprites by path (`Arc<Sprite>`, never evicted). Games read input by action name, never by physical key: `ctx.bind("jump", &[Key::Space, Key::Up])` (usually once, in the closure passed to `run`; binding again replaces) and then `input().down("jump")`, `pressed("jump")` (edge-triggered per fixed step, and a second key joining an already-held action is not a new press) and `axis("left", "right")`. Querying an action that was never bound panics, like a missing asset, so a typo cannot silently read as "not pressed". `key_down(Key)` is the raw escape hatch the engine itself uses for F3. Bindings can also live in a text file: one `action = Key Key` line each (`#` starts a comment, key names are the `minifb::Key` variant names, case-insensitive, listed once in `app/input.rs`). Games bind defaults in code, then call `ctx.load_bindings("input.txt")` to override them; a missing file is fine, while a malformed one returns `Err("path: line N: ...")` and applies nothing (games can just print it), because a player-edited file must not stop the game from starting. `ctx.save_bindings(path)` writes the bindings in the same format, sorted, but only the actions that differ from what the game had bound when it first called `load_bindings` (with no earlier `load_bindings`, all of them), so a default the game changes later still reaches players who remapped something else.

**Record and replay (`app/replay.rs`).** `ENGINE_RECORD=path` writes the run to a text file when it ends normally (window closed or the last scene quit; a killed process writes nothing): `seed N`, then one line per fixed step with the held keys, pad buttons, mouse position (or `-`) and five mouse-button digits. `ENGINE_REPLAY=path` starts with that seed instead of the clock's and, before each fixed step, overwrites the polled input with the recorded step (a bad file panics with its line number), then quits when the steps run out. The mouse position is recorded in canvas pixels, so a replay does not depend on the window size. Not recorded: analog pad axes, the wheel and typed characters, and the real keyboard still reaches the engine's own F3. It reproduces a run only if the game is deterministic: all randomness from `ctx.rng()` (seeded here) and no wall-clock reads; the physics is bit-for-bit repeatable (a test runs a pile three times and compares the bits). The text format round-trips and a tape's record and play-back are unit tested, and a hand-made file ending a run was tried with the camera example; a recorded real session has not been replayed.

**Save data (`app/save.rs`).** `Save` is a sorted `key = value` text file for game progress, separate from input bindings and owned by the game (not `Ctx`). `Save::load(path)` treats a missing file as empty and a malformed one as `Err("path: line N: ...")`; `set(key, impl ToString)`, `get::<T: FromStr>`, `get_or(key, default)`, `remove`; `save(path)` writes `path.tmp` and renames it over the target, so a crash mid-write keeps the old save. Newlines and backslashes in values are escaped; keys may not contain `=` or `#` (`set` panics, like an unbound action). Unparsable values read as missing.

**Fonts and Korean text (`render/bdf.rs`).** `gfx.text` stays the 8x8 ASCII font. For anything else, `ctx.assets().font(path)` loads a BDF bitmap font (`Font`, cached like sprites, panics on a bad file) and `gfx.text_font(&font, s, x, y, color)` draws a string; `font.width(s)` and `font.line_height()` measure it. The parser is in-house (no crate): it reads `FONT_ASCENT/DESCENT`, `ENCODING`, `DWIDTH`, `BBX` and `BITMAP` and ignores the rest, so any BDF works. All glyphs are packed once into a white-on-transparent atlas `Sprite`; each character becomes a `Paint::Mask { sheet, src, color }` command (atlas region tinted by `color`, ignores `Transform`), so colour is free and the GPU merges a string into one draw call. Chars missing from the font draw nothing and take no width. `assets/fonts/galmuri9.bdf` is Galmuri9 (SIL OFL, licence beside it) cut down to ASCII, the compatibility jamo and all 11172 Hangul syllables (1.07 MB; the full font is 2.5 MB, and the large-file hook in `.pre-commit-config.yaml` is raised to 2000 KB for this file). It used to hold only the 2350 KS X 1001 syllables, so about four in five syllables a player composed (every one of them passes through the text box while typing) drew as `?`; a test now checks that every syllable has a glyph. A character the font lacks (not Hangul, ASCII or jamo) is drawn and measured as `?`, and a font without `?` skips it. Regenerate it with a script that keeps those code points from the upstream `Galmuri9.bdf` and writes only `FONT_ASCENT/DESCENT` plus `ENCODING/DWIDTH/BBX/BITMAP` per glyph. `gfx.text_font_scaled(&font, s, x, y, scale, color)` draws every font pixel `scale` by `scale` (`Paint::Mask`'s destination rect is the source times a whole number: the software path repeats pixels, the GPU's nearest sampler does the same, and the parity scene covers it); `text_font` is scale 1, and `font.width` and `line_height` must be multiplied by `scale` by the caller.

**UI parts (`ui.rs`).** Immediate-mode helpers, no retained widget tree (input is keyboard actions, so a gamepad drives it too). `draw_panel(gfx, &rect, fill, border)` and `draw_bar(gfx, &rect, frac, color, back)` (frac clamped to 0..=1, whole pixels) record ordinary fills. `Menu::new(&["시작", "끝"])` is a vertical list: call `menu.update(ctx.input(), "up", "down", "accept")` once per fixed step (moves the highlight with wrap, returns `Some(index)` on an accept press) and `menu.draw(gfx, &font, x, y, color, active)` to draw it with a `Font`; the highlighted row gets a `>` marker and the `active` colour. The action names are the caller's, so every action must be bound. Mouse: `hovered(input, &rect)`, `clicked(input, &rect)` (left button press edge) and `slider(input, &rect, value) -> f32` (follows the cursor while the left button is held over the rect; dragging off it stops, so make the rect taller than the drawn track) are stateless; `menu.mouse(input, &font, x, y)` takes the same `x`/`y` as `draw`, highlights the row under a cursor that moved since the last step (a resting cursor must not fight the keyboard) and returns the index of a clicked row. Call both `update` and `mouse` in the same step if both inputs should work. `Rebind::new(input)` is a key remapping screen built on `Menu`: one row per bound action (`input.actions()`, `input.describe(action)`), Up/Down/Enter are fixed keys rather than actions (so remapping cannot lock the player out), Enter on a row waits for `input.key_just_pressed()` and binds it with `ctx.bind` (keys replaced, pad buttons kept), Escape cancels, and a row whose key another action also uses says so (`(also left)`; sharing is allowed, a menu and a game may both use Enter); `update(ctx)` returns true when a binding changed so the caller saves with `ctx.save_bindings`, and the caller must not treat Escape as back while `waiting()`. `Button::new(rect, label)` and `Checkbox::new(&font, (x, y), label, checked)` follow the same split as `Menu` because `Scene::update` has the input but no `Gfx` and `Scene::draw` has the `Gfx` but no input: call `update(ctx.input())` once per step (a button returns true on its click step, a checkbox on the step it flips, `checked` is a public field the game may also set) and `draw(gfx, &font)` in `draw`; the hover and held look is whatever the last `update` saw. A button centres its label and a checkbox's hit area covers the box and its text. No layout helpers: place rectangles by hand. `TextField::new(max)` is a one-line text box: `update(input)` appends `input().typed()` (printable characters since the last tick, taken from minifb's input callback so the layout and shift state are the window system's) up to `max` characters, removes one on a Backspace press and returns true on an Enter press; `draw(gfx, &font, x, y, color, caret)` draws the text and an optional `|`. No cursor movement, selection, clipboard or key repeat. There is no input method (minifb has no XIM support), so `TextField` composes Hangul itself with `src/hangul.rs`: every character goes through `Hangul::push`, which joins compatibility jamo into syllables the way a two-set keyboard does (vowel pairs such as ㅘ, final pairs such as ㄺ, a final moving to the next syllable when a vowel follows, Backspace removing one jamo at a time) and appends anything else unchanged; the syllable being typed is always the last character of the text, rewritten in place. Jamo arrive either from a Korean X layout (`setxkbmap kr`; not yet confirmed in a real window that minifb delivers them) or, after `set_korean(true)` (RightAlt toggles, shown by `korean()`), from letter keys mapped by `latin_to_jamo` (shift gives ㅃ ㅉ ㄸ ㄲ ㅆ ㅒ ㅖ). The limit counts characters and a step that would exceed it is undone whole. No hanja or candidate window. `examples/text.rs` shows it; the composing logic has unit tests, the real-window path has not been tried.

**Mouse.** Not action-bound: `input().mouse()` is `Some((x, y))` in logical canvas pixels (window pixels mapped through the letterbox, `None` over the black bars, camera not applied; `ctx.mouse_world()` adds the camera position, ignoring shake, for games with a scrolling view) or `None` outside the window; `mouse_down/pressed/released(MouseButton)` use the same per-step edges as keys, and `wheel()` is the wheel movement since the last tick. Widgets and games read it directly, so a gamepad has no equivalent.

**Gamepad (`app/pad.rs`).** `Pad` buttons (`A B X Y LB RB Back Start Up Down Left Right`) are bound to the same named actions as keys: `ctx.bind_pad("jump", &[Pad::A])` adds them beside the keys of that action (`bind` replaces only the keys, `bind_pad` only the pad buttons), and `down`/`pressed`/`axis` treat either as the action. In `input.txt` a pad button is `pad.<Name>` among the keys (`jump = Space pad.A`). No crate: `PadState` reads the Linux joystick API (`/dev/input/js0`, non-blocking, 8-byte events, Xbox-style numbering: buttons 0-7 are A B X Y LB RB Back Start, axes 0/1 the left stick, 6/7 the d-pad), retries opening once a second while nothing is plugged in, and drops back to "nothing held" if the device vanishes. The d-pad and the left stick (past about half deflection) both read as Up/Down/Left/Right, so the action API is digital. Analog values are separate: `input().pad_axis(PadAxis::LeftX | LeftY | RightX | RightY | LeftTrigger | RightTrigger)` gives sticks as -1..=1 with a 0.2 dead zone cut out and the rest rescaled, triggers as 0..=1 (axes 2 and 5, whose released value is -32767, so a pad that has sent nothing reads 0), and 0 with no pad; they are not bound to actions, y points down like the screen. One pad, no rumble. On other OSes it reports nothing. The event decoding and axis scaling are tested with synthetic events; they have not been run against real hardware (the trigger and right-stick axis numbers are the Xbox layout and unconfirmed) (WSL exposes no `/dev/input`).
